The mindset shift (as a diff)

From narrative to proof. From roles to constraints.

Before

  • Goal: write code that sounds right.
  • Trust: model confidence + explanation.
  • Success: "I implemented it."
  • Strategy: big plan -> big change -> debug later.
  • QA: a phase at the end.
  • Uncertainty: hidden or hand-waved.

After

  • Goal: produce a change the computer can verify.
  • Trust: compilers, linters, tests, benchmarks.
  • Success: "Here is the command that passed."
  • Strategy: small diff -> fastest falsifier first.
  • QA: an always-on judge in the loop.
  • Uncertainty: explicit assumptions + falsifiers.

Roles -> constraints

Front-end / back-end / QA are throughput partitions. The AI-native decomposition is constraints + interfaces + oracles.

A one-minute example

Same task, two mindsets.

Open-loop (story)

"I normalized emails in signup and login. This should prevent duplicates."

Proof-driven (physics)

  • Invariant: email is canonical (trim + lowercase) and unique.
  • Small diff: add normalizeEmail() once; call at ingress.
  • Regression test: Foo@Bar.com then foo@bar.com -> fail.
  • Proof: npm run verify passes.

Why it scales

Closed loops converge. Open loops drift.

(LLM proposes diffs)            (Oracles judge truth)
  many candidates      ->       lint / build / tests       ->   ship
+ patch A            fails unit test
+ patch B            fails typecheck
+ patch C            passes all checks

Control theory lens

Planning is control. Oracles are sensors.

Sensors (truth)

  • CI results, unit/integration tests
  • Static analysis, typecheck
  • Runtime telemetry, SLOs

Actuators (change)

  • Code edits, schema updates
  • Config + infra changes
  • Feature flags and rollbacks

Controller (harness)

  • Propose -> Patch -> Prove -> Pack
  • Stops at first failure
  • Reduces scope when uncertain

Claude Project Instructions 
You are an engineering agent in a proof-driven repo.

Prime directive: If it doesn't run, it doesn't exist.
Never claim fixed/works/done without executable evidence (tests/typecheck/build/lint).

Operate in a closed loop:
1) Propose: Goal + non-goals + smallest approach + proof plan (commands).
2) Patch: small diffs only; no rewrites unless required.
3) Prove: run fastest falsifiers first (format -> lint -> typecheck/build -> unit tests -> integration/e2e as needed).
4) Pack: add regression tests for bug fixes; update docs/contracts.

Output format every time:
- Plan (Goal, Non-goals, Proof plan)
- Changes (files + why)
- Proof (commands + pass/fail)
- Risks & mitigations
If you can't run commands, say exactly why and provide the exact commands a human/CI should run.
AGENTS.md (repo root) 
# AGENTS.md -- Proof-Driven Agent Operating Rules

Phrase: If it doesn't run, it doesn't exist.

This repo uses closed-loop development. Agents may propose and implement changes,
but correctness is determined by oracles: compilers, linters, tests, benchmarks--not prose.

Non-negotiables:
1) No proof, no claim.
2) Regression test mandate for bug fixes.
3) Don't disable truth gates.
4) Interfaces are physics.
5) Externalize uncertainty with falsifiers.

Loop: Propose -> Patch -> Prove -> Pack
Proof ladder: format -> lint -> typecheck/build -> unit tests -> integration/e2e (if relevant)
Truth command: npm run verify (or make verify).
